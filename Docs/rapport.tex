\section{Introduction}
\label{sec:intro}

\subsection{Context and Objectives}

Quantum Bluff was developed as part of the final third-year Bachelor's degree project (L3 Computer Science, French academic system) at the University of Strasbourg. The objective was to deliver a \textbf{real-time multiplayer gaming platform} with a professional-grade engineering posture: modular architecture, automated testing, observability hooks, security hardening, and collaborative delivery under time constraints.

The \textbf{initial product intent} (before scope expansion) was a Texas Hold'em poker platform: practice mode against AI with multiple difficulty levels, multiplayer cash tables (public/private), configurable blinds, minimum buy-in rules, a probability-oriented HUD, and a \textbf{hidden side-bet} subsystem. The technical goals included authoritative server-side rules, transactional chip movements, WebSocket-scale event delivery, and operational readiness (health checks, metrics, recovery paths).

Security and reliability were first-class constraints from the outset: JWT authentication, optional TOTP 2FA, anti-cheat and rate-limiting layers, idempotent handling for sensitive mutations, and schema validation on critical API paths.

\subsection{Scope of this document}

This report summarizes \textbf{management evolution}, \textbf{tooling}, \textbf{delivered capabilities}, and \textbf{architecture}. Exhaustive technical narratives (bots, probabilities, tournaments, hidden bets, etc.) are deferred to \textbf{Appendices A--M} to avoid repetition. Repository-relative file paths use \verb|\path{...}| notation.

\section{Project Evolution}
\label{sec:evolution}

\subsection{Initial specifications (poker-first)}

The early scope targeted: Texas Hold'em cash games; \textbf{AI practice} with four difficulty tiers (\texttt{easy}, \texttt{medium}, \texttt{hard}, \texttt{expert}) enforced in \path{server/src/routes/game.api.routes.ts} and \path{server/src/routes/bot.routes.ts}; public/private multiplayer rooms with SB/BB configuration and minimum balance rules; \textbf{real-time} updates via Socket.IO; a \textbf{Quantum HUD} for win-equity and hand-category feedback (\path{client/src/components/QuantumHUD.tsx}); and \textbf{hidden bets} resolved server-side (\path{server/src/poker/hiddenBets/}).

\subsection{Scope expansion (casino, tournaments, social, progression)}

The delivered system adds: \textbf{Blackjack} solo and \textbf{multi-table} lobbies (\path{client/src/pages/Blackjack.tsx}, \path{client/src/pages/BlackjackMultiLobby.tsx}, \path{client/src/pages/BlackjackMultiTable.tsx}); \textbf{slot} and \textbf{roulette} flows reachable from the mini-games hub (\path{client/src/pages/MiniGames.tsx}); \textbf{tournaments} with waiting room, in-tournament table, results, and \textbf{winner prediction side bets} (\path{client/src/features/tournament/}); \textbf{leaderboards}; \textbf{XP}, badges, daily challenges, daily login streak; \textbf{friends}, invitations, join requests, \textbf{peer loans} with interest/repayment hooks; \textbf{profile} editing with server-stored avatars; \textbf{2FA TOTP}; \textbf{feedback} and \textbf{player reports}; \textbf{wallet ledger}, gift codes, and dev recharge helpers; \textbf{i18n} in five locales (\path{client/src/i18n/locales/}); \textbf{tutorial} flow (\path{client/src/pages/TutorialGame.tsx}, \path{client/src/features/tutorial/}); \textbf{admin web console} and packaged targets (\textbf{Electron}, \textbf{Capacitor}) per \path{client/package.json}.

\subsection{Why the narrative moved from ``catalog'' to ``appendices''}

The codebase grew across \textbf{client}, \textbf{server}, \textbf{database}, and \textbf{docs/} technical notes. Listing every subsystem in prose would duplicate \path{docs/ARCHITECTURE.md} and the structured logic notes under \path{Docs/detail_logique/}. The body therefore stays outcome-oriented; appendices map each major subsystem to code anchors.

\section{Project Management}
\label{sec:management}

\subsection{Initial V-model phase}

The project began with a \textbf{V-model style} framing: business requirement gathering with end users in mind, benchmarking comparable products, brainstorming sessions \textbf{validated collectively} by the team, and a written requirements package plus an initial Gantt chart. A \textbf{technical lead} was appointed to structure the MOE (implementation) track while the project manager covered the MOA (needs, prioritization, specification) track until the specification baseline stabilized.

\subsection{Transition to an agile-inspired workflow (Jira, Scrum practices)}

After an intensive early phase (approximately \textbf{two months} of V-model-oriented execution on a \textbf{four-month} calendar), the team concluded that strict phase separation slowed integration of new gameplay and infrastructure ideas. The organization shifted toward an \textbf{iterative, Scrum-inspired workflow}: \textbf{Jira} for epics, user stories, and time-boxed sprints; backlog ordering by \textbf{value vs.\ risk}; twice-weekly synchronization meetings for decisions, unblockers, and demo-ready increments. The project manager studied agile practice material (including \textit{Scrum Life}) to align rituals with the team's reality rather than copying a textbook process wholesale.

\subsection{Planning, coordination, and reporting}

Coordination relied on: recurring meetings (\textasciitilde{}twice per week), shared technical documentation under \path{Docs/}, internal validation sessions, and continuous integration feedback via \path{.gitlab-ci.yml} at the repository root. Work was distributed dynamically across frontend, backend, and infrastructure tasks because multiplayer features require tight coupling between UI state, socket events, and persistence.

\subsection{Product management mechanics}

Backlog prioritization balanced user-visible value (new game modes, social features) against enabling work (Redis adapter, rate limits, recovery jobs, observability). Cross-cutting concerns (security, idempotency, anti-cheat) were escalated early to avoid late integration risk.

\section{Development Tools and Technologies}
\label{sec:tools}

\subsection{Frontend and backend}

\textbf{Client:} React 19, TypeScript, Vite 7, Tailwind CSS, Radix UI primitives (\path{client/src/components/ui/}), react-router-dom v7, Redux Toolkit with RTK Query (\path{client/src/services/api.ts}), socket.io-client (\path{client/src/services/socket.ts}), i18next (\path{client/src/i18n/config.ts}).

\subsection{Database and infrastructure}

Local PostgreSQL via \path{database/docker-compose.yml}. Redis for multi-instance coordination and abuse controls. Optional OpenTelemetry and Prometheus-oriented metrics endpoints (\path{server/src/observability/}).

\subsection{Version control and collaboration}

Git repository with GitLab CI configuration at \path{.gitlab-ci.yml}. Documentation and logic notes live under \path{Docs/} (including \path{docs/ARCHITECTURE.md} and \path{Docs/detail_logique/}).

\subsection{Testing and deployment}

Client: Vitest, Playwright (\path{client/e2e/}). Server: Jest and Supertest (\path{server/src/__tests__/}). Desktop/mobile packaging: Electron and Capacitor scripts in \path{client/package.json}.

\section{Use of Artificial Intelligence}
\label{sec:ai}

\subsection{In-product AI: poker bots}

The shipped product includes \textbf{heuristic poker bots} with configurable difficulty. Core decision logic lives in \path{server/src/logic/botAI.ts}, orchestrated HTTP services in \path{server/src/services/botAi.service.ts}, and practice-mode integration (\path{server/src/poker/services/practiceBotTurns.service.ts}). Difficulty is part of the validated API contract (\path{server/src/routes/bot.routes.ts}).

\subsection{AI-assisted engineering (tooling)}

Team members used modern \textbf{coding assistants} (e.g., IDE-integrated LLMs) for drafting, refactors, and documentation. Generated output was treated as \textbf{untrusted}: reviewed in merge requests, validated by automated tests, and rejected when it contradicted server authority or security invariants.

\subsection{Limits and verification}

Bots are \textbf{not} opaque learned models in production: they are inspectable code paths. Assistant-generated snippets were never merged without human review and test signal.

\section{System Architecture}
\label{sec:architecture}

\subsection{Monorepo layout}

The repository splits into \path{client/} (Vite SPA), \path{server/} (Express + Socket.IO gateway), and \path{database/} (local Postgres). Client bootstraps providers in \path{client/src/main.tsx} and routes in \path{client/src/App.tsx}. Server composes middlewares and REST mounts in \path{server/src/index.ts}, then attaches \path{server/src/sockets/game.gateway.ts} to the HTTP server.

\subsection{Real-time communication}

Socket.IO uses path \texttt{/socket.io}. Authentication mirrors REST JWT validation (\path{server/src/middleware/socketAuth.middleware.ts}). Redis adapter enables horizontal scale-out when Redis is available.

\subsection{Persistence and integrity}

Prisma models capture users, games, tournaments, loans, hidden bet tickets, wallet ledger rows, and more (see \path{server/prisma/schema.prisma}). Critical monetary flows favor server-side orchestration and short transactions.

\section{Security, Testing and Stability}
\label{sec:security}

\subsection{Authentication and abuse controls}

JWT on HTTP and sockets; optional TOTP 2FA (\path{server/src/routes/twofa.routes.ts}); Helmet and CORS allowlists (\path{server/src/index.ts}); segmented rate limits for bot, slot, roulette, blackjack, hidden-bets, and multi-blackjack routes; anti-cheat middleware and gateway-side monitors (\path{server/src/services/antiCheat.service.ts}, \path{server/src/sockets/game.gateway.ts}); idempotency middleware for sensitive mutations (\path{server/src/middleware/idempotency.middleware.ts}).

\subsection{Testing and debugging}

Broad automated coverage on server and client; Playwright smoke tests. Additional manual scenarios are documented under \path{Docs/POKER_SCENARIOS.md} and related files.

\subsection{Performance and stability}

Redis-backed Socket.IO adapter, structured logging, Prometheus metrics endpoint, readiness endpoints, graceful shutdown hooks (\path{server/src/index.ts}).

\section{Technical Challenges}
\label{sec:challenges}

\textbf{Concurrency around shared tables:} poker and blackjack runtimes use locking strategies (see \path{server/src/poker/services/pokerTableLock.service.ts} and blackjack lock services) to prevent split-brain chip mutations.

\textbf{Recovery after process restarts:} blackjack and tournament subsystems implement recovery services invoked at boot (\path{server/src/index.ts}).

\textbf{Hidden bet settlement coupling:} market resolution must align with poker street transitions; implemented in hidden-bet resolver modules (Appendix~\ref{app:hidden}).

\textbf{Internationalization without clobbering user preference:} guest screens (StartScreen, Auth, global loader) force English using \texttt{react-i18next} with a fixed \texttt{lng: 'en'} override so the global language stored for authenticated use is unchanged (\path{client/src/pages/Auth.tsx}, \path{client/src/contexts/LoaderContext.tsx}).

\section{Conclusion}

Quantum Bluff exceeded its initial poker-only charter by integrating multiple casino modes, tournaments, social lending, progression systems, and operational hardening while keeping a monorepo with clear separation between UI, API, and authoritative game logic. The project demonstrates that a student team can approach industry-like constraints---real-time state, monetary integrity, security, and observability---when management explicitly trades early waterfall rigidity for controlled agile iteration.
