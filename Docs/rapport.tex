\section*{Abstract}
\addcontentsline{toc}{section}{Abstract}

\noindent
Quantum Bluff is a capstone web platform produced for the third-year Bachelor's degree in Computer Science (L3) at the University of Strasbourg. It combines an authoritative Texas Hold'em stack with extended casino-style modules (solo and multiplayer blackjack, slots, European roulette), structured tournaments with ancillary winner markets, social features (friends, invitations, peer loans), and progression systems (XP, daily challenges, leaderboards). This report explains how delivery evolved from an initial V-model framing to an agile-inspired workflow; which engineering tools preserved modularity and testability; and how runtime architecture separates the React client, Express REST endpoints, a Socket.IO gateway, Prisma-backed persistence, and Redis-backed coordination. Security controls (JWT and optional TOTP, segmented rate limits, idempotency on sensitive mutations, anti-cheat hooks) and an automated test harness are summarized alongside appendices that map each major domain to repository artefacts. The product uses \textbf{virtual chips} for pedagogical demonstration; it does not implement real-money gambling.

\section{Introduction}
\label{sec:intro}

\subsection{Context and Objectives}

Quantum Bluff was developed as part of the final third-year Bachelor's degree project (L3 Computer Science, French academic system) at the University of Strasbourg. The objective was to deliver a \textbf{real-time multiplayer gaming platform} with a professional-grade engineering posture: modular architecture, automated testing, observability hooks, security hardening, and collaborative delivery under time constraints.

The \textbf{initial product intent} (before scope expansion) was a Texas Hold'em poker platform: practice mode against AI with multiple difficulty levels, multiplayer cash tables (public/private), configurable blinds, minimum buy-in rules, a probability-oriented HUD, and a \textbf{hidden side-bet} subsystem. The technical goals included authoritative server-side rules, transactional chip movements, WebSocket-scale event delivery, and operational readiness (health checks, metrics, recovery paths).

Security and reliability were first-class constraints from the outset: JWT authentication, optional TOTP 2FA, anti-cheat and rate-limiting layers, idempotent handling for sensitive mutations, and schema validation on critical API paths.

This report summarizes \textbf{management evolution}, \textbf{tooling}, \textbf{delivered capabilities}, and \textbf{architecture}. \section{Project Management}
\label{sec:management}

\subsection{Initial V-model phase}

The project began with a \textbf{V-model style} framing: business requirement gathering with end users in mind, benchmarking comparable products, brainstorming sessions \textbf{validated collectively} by the team, and a written requirements package plus an initial Gantt chart. A \textbf{technical lead} was appointed to structure the MOE (implementation) track while the project manager covered the MOA (needs, prioritization, specification) track until the specification baseline stabilized.

\subsection{Transition to an agile-inspired workflow (Jira, Scrum practices)}

After an intensive early phase (approximately \textbf{two months} of V-model-oriented execution on a \textbf{four-month} calendar), the team concluded that strict phase separation slowed integration of new gameplay and infrastructure ideas. The organization shifted toward an \textbf{iterative, Scrum-inspired workflow}: \textbf{Jira} for epics, user stories, and time-boxed sprints; backlog ordering by \textbf{value vs.\ risk}; twice-weekly synchronization meetings for decisions, unblockers, and demo-ready increments. The project manager studied agile practice material (including \textit{Scrum Life}) to align rituals with the team's reality rather than copying a textbook process wholesale.

\subsection{Planning, coordination, and reporting}

Coordination relied on: recurring meetings (\textasciitilde{}twice per week), shared technical documentation under \path{Docs/}, internal validation sessions, and continuous integration feedback via \path{.gitlab-ci.yml} at the repository root. Work was distributed dynamically across frontend, backend, and infrastructure tasks because multiplayer features require tight coupling between UI state, socket events, and persistence.

\subsection{Product management mechanics}

Backlog prioritization balanced user-visible value (new game modes, social features) against enabling work (Redis adapter, rate limits, recovery jobs, observability). Cross-cutting concerns (security, idempotency, anti-cheat) were escalated early to avoid late integration risk.

\section{System Architecture}
\label{sec:architecture}

\subsection{Monorepo layout}

The repository splits into \path{client/} (Vite SPA), \path{server/} (Express + Socket.IO gateway), and \path{database/} (local Postgres). Client bootstraps providers in \path{client/src/main.tsx} and routes in \path{client/src/App.tsx}. Server composes middlewares and REST mounts in \path{server/src/index.ts}, then attaches \path{server/src/sockets/game.gateway.ts} to the HTTP server.

\subsection{Real-time communication}

Real-time communication is one of the central parts of Quantum Bluff. A poker or blackjack game cannot work correctly if players have to refresh the page after every action. Bets, folds, turns, invitations, waiting-room changes and tournament assignments must appear immediately for all concerned users. For this reason, the project uses Socket.IO on the \texttt{/socket.io} path, while still keeping REST endpoints for durable actions such as authentication, profile updates, friendship operations or tournament registration.

The most important design choice is the \textbf{authoritative server} model. In simple terms, the browser is allowed to say ``I want to do this action'', but it is never allowed to decide that the action is valid. For example, the client can request a call, a fold, a table join, or a blackjack move, but the server verifies the user identity, the current game state, the turn order, the chip balance, the table capacity and the game rules before accepting it. This is essential in a card platform because private cards, pot distribution, hidden side bets and player balances must not depend on code running inside the user's browser.

The socket authentication flow follows the same identity logic as the REST API. A player sends a JWT either in \texttt{handshake.auth.token} or through an \texttt{Authorization: Bearer ...} header. This token is validated by \path{server/src/middleware/socketAuth.middleware.ts} and then rechecked in important gateway paths inside \path{server/src/sockets/game.gateway.ts}. The server rejects malformed tokens, revoked tokens, invalid issuer/audience/type values, admin tokens used on player sockets, missing database users and suspended accounts. Only after these checks does the socket receive a trusted \texttt{socket.userId}. This matters because later real-time events do not blindly trust a \texttt{playerId} sent by the client; they compare it with the authenticated socket identity.

Socket.IO rooms are used to deliver events only to the users who need them. Each connected user joins a private room named \texttt{user:\{userId\}}, which is used for personal notifications such as friend requests, invitations, warnings, tournament assignments and moderation-related messages. Game tables also have their own rooms, so a poker table update is broadcast to the table participants rather than to every connected browser. Tournaments use rooms such as \texttt{tournament:\{id\}} for roster updates, starts, next rounds, cancellations and final results. This keeps communication organized and avoids mixing unrelated users' events.

Game synchronization is based on two complementary mechanisms: \textbf{events} and \textbf{snapshots}. Events are useful for immediate changes, for example ``a player joined'', ``a player acted'', ``the round advanced'', or ``the roster changed''. However, relying only on small incremental events is fragile: if a user refreshes the page, temporarily loses connection, or misses one event, the local UI can become inconsistent. To avoid this, the gateway sends a complete sanitized snapshot when a user joins or reconnects. For poker, live runtime controllers are tracked through \path{server/src/shared/activeGames.ts}, and serializable snapshots are stored through \path{server/src/shared/pokerStateStore.ts} and \path{server/src/poker/services/pokerStateSync.service.ts}. For blackjack, equivalent recovery and snapshot logic exists under \path{server/src/blackjack/recovery/} and \path{server/src/blackjack/services/}.

The word \textit{sanitized} is important. A snapshot is not just a copy of the server memory. It is a version of the state prepared for a specific recipient. A seated poker player can receive their own private cards; other players and spectators cannot. A user can see public table state, pot information and visible cards, but hidden information remains hidden. This gives the user interface enough data to render the game while preserving confidentiality and fairness.

Real-time communication is also used outside the game table. The lobby receives live information about rooms, friends, invitations and daily activity. The friends system can notify a user immediately when a friend request is received or accepted. The blocked-user warning flow also uses real-time communication: if a user tries to join a room containing a blocked member, or if a blocked member joins after them, the client receives a warning and can choose whether to continue. This shows that Socket.IO is not only used for cards; it supports the whole multiplayer experience around the game.

Redis support allows the Socket.IO layer to work beyond a single Node.js process. The adapter configured in \path{server/src/config/socketIoRedis.ts} lets events be propagated across instances, which is important for deployment scenarios where multiple server processes may handle different users. For local development or degraded conditions, the system can still run with a local fallback, but the production-oriented design is ready for distributed event delivery.

Overall, the real-time solution is designed around three principles: the server remains the source of truth, each user receives only the state they are allowed to see, and reconnection is treated as a normal situation rather than as an exceptional failure. This makes the application understandable for users, safer against modified clients, and more stable during real multiplayer sessions.

Prisma models capture users, games, tournaments, loans, hidden bet tickets, wallet ledger rows, and more (see \path{server/prisma/schema.prisma}). Critical monetary flows favor server-side orchestration and short transactions.

\section{Security, Testing and Stability}
\label{sec:security}

\subsection{Authentication and anti-cheat}

Authentication is the part of the system that answers a simple question: ``who is this user, and are they allowed to do this?'' In Quantum Bluff, this question is asked not only on normal HTTP routes, but also on Socket.IO connections and game actions. This is important because a multiplayer game exposes many sensitive operations: joining rooms, betting chips, sending invitations, changing profile data, reporting users and accessing admin information.

The main authentication mechanism uses short-lived JWT access tokens generated by \path{server/src/auth/jwt.service.ts}. A JWT is a signed token that proves the server has authenticated the user. In this project, the token must have the expected issuer, audience, signature algorithm and \texttt{type: access}. Its subject is aligned with the user id. HTTP routes only accept the standard \texttt{Authorization: Bearer ...} format; raw tokens or malformed headers are rejected early by the bearer-token extraction logic. This avoids ambiguous token parsing and makes the API behavior predictable.

Protected REST routes pass through \path{server/src/middleware/auth.middleware.ts}. This middleware does several checks instead of only decoding the token. It verifies that the token has not been revoked, validates the JWT signature and metadata, rejects admin-role tokens on player routes, checks that the user still exists in PostgreSQL, and blocks suspended accounts with an explicit \texttt{ACCOUNT\_SUSPENDED} response. This means that deleting or suspending an account is effective even if an old token still exists on the client side.

Passwords are never stored in clear text. Registration and password changes are handled in \path{server/src/routes/auth.routes.ts}, where passwords are hashed with bcrypt before persistence. The accepted password format is validated with Zod schemas from \path{server/src/validation/auth.validation.ts}. The policy requires enough length and complexity, including uppercase, numeric and special-character requirements. The goal is not only to reject weak passwords, but also to centralize the rule so registration, reset and profile password changes stay consistent.

The account layer also includes optional TOTP two-factor authentication in \path{server/src/routes/twofa.routes.ts}. TOTP is the mechanism used by applications such as Google Authenticator or Authy: after entering the password, the user must also provide a short code generated on a trusted device. Pending setup secrets are stored temporarily in Redis, and disabling 2FA requires both the current password and a valid one-time code. This prevents a stolen session alone from silently disabling the second factor.

Logout and token revocation are handled by \path{server/src/auth/tokenBlacklist.ts}. Instead of storing the raw token in Redis, the implementation stores a hash of the token with an expiration time. This allows the server to reject a token after logout while avoiding unnecessary storage of sensitive token material. An in-memory fallback exists for degraded development conditions, but Redis is the intended shared store when several processes are running.

The same identity model is enforced on WebSocket traffic. \path{server/src/middleware/socketAuth.middleware.ts} rejects revoked tokens, invalid JWTs, admin tokens, missing users and suspended accounts before a socket can interact with game rooms. Then, in \path{server/src/sockets/game.gateway.ts}, sensitive events compare the trusted \texttt{socket.userId} with any player id included in the event payload. If a modified client tries to act for another player, the mismatch is refused and logged. This protects actions such as joining a game, reconnecting, accepting invitations or sending poker actions.

Anti-cheat is implemented as a set of layered controls rather than a single magic function. At the HTTP level, \path{server/src/middleware/antiCheat.middleware.ts} checks whether the authenticated user is currently banned, records the last observed IP address, and delegates suspicious-pattern detection to \path{server/src/services/antiCheat.service.ts}. This service can raise alerts when several distinct accounts appear from the same non-local IP address or when reaction times are unrealistically fast. Repeated alerts can lead to a temporary suspension through the \texttt{bannedUntil} field.

At the real-time game level, \path{server/src/utils/antiCheat.ts} tracks action bursts. For example, more than eight actions in a three-second window is considered suspicious by default. The poker action handler can refuse excessive actions and record the incident. This is useful because some abuses do not appear during login; they appear during gameplay, when a script or modified client sends actions faster than a normal player could.

The project also protects against social and room-abuse scenarios. Blocked users are filtered from friend search, blocked relationships can trigger warnings before joining rooms, and player reports are persisted so administrators can review them. This connects security with moderation: the system is not only trying to stop technical attacks, but also to give users tools against unwanted interactions.

Additional hardening is applied at the application boundary. \path{server/src/index.ts} configures Helmet headers and CORS allowlists. Segmented rate limits protect authentication, bot routes, slot, roulette, blackjack, hidden bets and multiplayer blackjack endpoints. Sensitive mutations can use idempotency middleware from \path{server/src/middleware/idempotency.middleware.ts}, which helps prevent duplicate chip-changing requests when a user retries or refreshes at the wrong moment. Admin routes are separated from player routes and require the appropriate role.

In summary, the security strategy follows a defence-in-depth approach. Each layer checks what it can know best: validation schemas check input shape, authentication middleware checks identity, socket middleware checks connection trust, game services check rule legality, anti-cheat services check suspicious behavior, and admin tools expose reports and alerts for review. For an academic prototype, this gives a strong and coherent security baseline. A public production launch would still require a professional penetration test, secret rotation procedures and long-term monitoring, but the implemented project already covers the main authentication and anti-cheat risks expected in this scope.

\section{Technical Challenges}
\label{sec:challenges}

\textbf{Concurrency around shared tables:} poker and blackjack runtimes use locking strategies (see \path{server/src/poker/services/pokerTableLock.service.ts} and blackjack lock services) to prevent split-brain chip mutations.

\textbf{Recovery after process restarts:} blackjack and tournament subsystems implement recovery services invoked at boot (\path{server/src/index.ts}).

\textbf{Hidden bet settlement coupling:} market resolution must align with poker street transitions; implemented in hidden-bet resolver modules (Appendix~\ref{app:hidden}).

\textbf{Internationalization without clobbering user preference:} guest screens (StartScreen, Auth, global loader) force English using \texttt{react-i18next} with a fixed \texttt{lng: 'en'} override so the global language stored for authenticated use is unchanged (\path{client/src/pages/Auth.tsx}, \path{client/src/contexts/LoaderContext.tsx}).

\subsection{Implemented solutions}

The implemented solution is a complete web platform rather than a single isolated poker prototype. The project was organized into domain modules that share the same runtime architecture: a React and TypeScript client for the interface, an Express API for REST operations, Socket.IO for real-time communication, Prisma with PostgreSQL for durable storage, and Redis for coordination features such as token revocation, rate limiting and distributed socket events. This structure makes the project easier to understand: the client displays and sends user intentions, while the server validates, computes, persists and broadcasts the result.

For the poker core, the solution is server authority. The server owns the real table state, including seats, blinds, current street, legal actions, pots, side pots, showdowns and chip movements. The client does not decide who wins, how much a player receives, whether an action is legal, or whether a hidden side bet is valid. Poker actions pass through the gateway and \path{server/src/poker/services/pokerActionOrchestrator.service.ts}; the table logic itself is implemented under \path{server/src/logic/}. This gives the game a clear trust model: the browser is an interface, not the referee.

Hidden bets were implemented as a separate server-side subsystem under \path{server/src/poker/hiddenBets/}. This avoids mixing side-market logic directly into the main poker table. Pricing, placement, settlement and ledger effects are handled by dedicated services, and the resolver follows poker street transitions. This design keeps hidden bets attached to the real poker result while reducing the risk of leaking private information to the client.

For real-time synchronization, the project combines Socket.IO events, rooms, snapshots and recovery stores. Important changes are emitted to the relevant room, but reconnecting clients also receive a full sanitized snapshot. Poker snapshots are serialized through \path{server/src/poker/services/pokerStateSync.service.ts} and stored through \path{server/src/shared/pokerStateStore.ts}; active games are tracked in \path{server/src/shared/activeGames.ts}. Blackjack has its own snapshot and recovery services under \path{server/src/blackjack/}. This solution addresses a common multiplayer problem: a user who refreshes or reconnects should not be stuck with an old local state.

For blackjack, the project supports both solo and multiplayer experiences. Solo blackjack is a server-controlled loop where the user plays against the dealer. Multiplayer blackjack uses rooms, seats, invitations, snapshots, recovery and table-specific events. The logic remains separate from poker because blackjack has different rules, different round flow and different UI needs. At the same time, it still follows the same project principles: server-side validation, controlled chip updates and real-time user feedback.

For roulette and slot machine features, the solution was to keep the casino mini-games isolated behind their own logic modules and API routes. The server calculates outcomes, validates stakes, applies caps and updates wallet state. The frontend renders the experience and displays history or results, but it does not determine payouts. This keeps the virtual economy coherent across poker, blackjack, roulette and slots.

For tournaments, the implementation separates the lifecycle into clear phases: creation, registration, waiting room, table assignment, round progression, elimination, completion and reward distribution. The frontend feature package lives under \path{client/src/features/tournament/}, while server-side orchestration lives under \path{server/src/tournament/}. Socket.IO rooms such as \texttt{tournament:\{id\}} and \texttt{user:\{userId\}} notify players about roster changes, starts, next rounds, kicks, cancellations and results. Tournament winner side bets are handled by their own services so settlement remains tied to the real tournament outcome.

For the lobby, the implemented solution was to make it the main operational screen of the application. After login, the user can see and join poker rooms, blackjack rooms, tournaments, friends, invitations and daily activity without navigating through a marketing-style landing page. The lobby also integrates social actions such as friend status, direct invitations, blocked-user warnings and live room updates. This makes the application feel like a multiplayer platform rather than a collection of disconnected pages.

For the friends and moderation system, the solution combines persistent REST operations with live notifications. Users can send and receive friend requests, remove friends, block users, unblock them from a blocked list, report players with a reason, open chat interactions and receive warnings when joining rooms containing blocked users. Reports and moderation data are stored server-side so they can be reviewed by administrators. This feature is important because a multiplayer application needs user-safety tools, not only game logic.

For progression and retention, XP, badges, daily challenges, daily login streaks, leaderboards, gift codes and recharge flows were implemented as separate modules. The user can see progress and rewards in the interface, but server-side services remain responsible for eligibility, caps and balance-changing effects. This prevents the progression system from becoming only a visual layer and keeps it connected to the persistent user profile.

For authentication, security and anti-cheat, the solution is intentionally layered. HTTP middleware, socket middleware, gateway checks, validation schemas and domain services all verify different parts of the same trust chain. A forged REST body cannot replace the authenticated JWT identity. A forged socket payload cannot act as another player. A suspended user is blocked during authentication, REST access and socket connection. Suspicious behavior is logged and can lead to anti-cheat alerts or temporary suspension. This redundancy is useful because security mistakes often happen when only one layer is trusted too much.

For monetary integrity, every chip-changing operation is treated as sensitive. The project uses server-side settlement, Prisma persistence, transaction-oriented patterns, wallet ledger rows, idempotency keys where needed, and domain-specific services for rewards or payouts. This is visible in casino games, hidden bets, tournament rewards, social loans and wallet updates. The shared rule is simple: the balance shown in the browser is only a display; the database and server services are the real source of truth.

For the interface, the solution was to build functional screens around the user's actual workflows: lobby, poker table, blackjack, roulette, mini-games, friends, profile, leaderboard, tournaments and admin console. Reusable components and shared services reduce duplication. Internationalization uses i18next resources, and the application includes multiple locales. Accessibility, theming, music/effects settings and responsive layout work were added so the interface is not only technically functional, but also usable in realistic conditions.

For deployment and operations, the project includes Docker-oriented local setup, PostgreSQL, Redis, Nginx-related configuration, GitLab CI and production documentation. Health checks, metrics-oriented code and graceful shutdown behavior are part of the server infrastructure. These elements help move the project from a local student prototype toward something that can be deployed, tested and maintained.

For validation, automated tests cover important pure logic, validation schemas, tournament helpers, gateway behavior, waiting-room identity checks, recovery logic and several API flows. The CI pipeline acts as a regression gate for merge requests. Manual validation documents and scenario files complement automated tests for flows that are difficult to cover completely, such as full multiplayer sessions. The result is not only a feature-complete implementation, but a project with traceability between the implemented modules, the reported architecture and the expected user behavior.

The remaining work before a real public release would be external security auditing, longer load testing, a formal data-protection review, more end-to-end coverage for complete user journeys, and a polished production observability dashboard. For the academic scope of the project, however, the implemented solution covers the main functional, real-time, security, social, economy, gameplay and deployment needs of the platform.

\subsection{Strength signal and decisions}

Let $H$ be the scalar hand score returned by \texttt{getHandValue} for the bot's visible cards (two to seven cards). The code normalizes
\[
\sigma = \min\Bigl(1,\,\max\bigl(0,\, H/S_{\max}\bigr)\Bigr),
\qquad

\]

The easy tier, for example, injects naive bluffs on a free street with fixed probability and biases calls when facing small bets with medium strength.

\section{Probabilities, Quantum HUD, and Monte Carlo helper}
\label{app:hud}

\subsection{Division of responsibilities}

The \textbf{Quantum HUD} (\path{client/src/components/QuantumHUD.tsx}, context \path{client/src/contexts/QuantumHUDContext.tsx}) displays \textit{estimates} for the authenticated player. These are computed client-side for responsiveness and are \textbf{not} used to settle real-money outcomes (the product uses virtual chips). Server-side hidden-bet pricing uses separate tabular services (Appendix~\ref{app:hidden}).

\subsection{Monte Carlo equity estimator}

Implementation file: \path{client/src/utils/pokerMonteCarloEquity.ts}. Let $N$ be the number of iterations (default $N=2000$, constant \texttt{MONTE\_CARLO\_DEFAULT\_ITERATIONS}). For each iteration the code:
\begin{enumerate}
\item Builds the remaining deck excluding known hero and community cards (\texttt{buildDeckExcluding}).
\item Draws, without replacement, the missing board cards and $2\times n_{\mathrm{opp}}$ opponent hole cards using a partial Fisher--Yates swap sampler (\texttt{drawWithoutReplacement}).
\item Evaluates the hero and each opponent seven-card hand with \texttt{evaluateSevenEval} (same taxonomy as the server evaluator).
\item Splits the simulated pot equally among all players that achieve the best score.
\end{enumerate}
If $S_t \in \{0, 1/k\}$ is the hero's share on iteration $t$ when $k$ players tie for the best score, the reported equity is
\[
\hat{e} = \frac{1}{N}\sum_{t=1}^{N} S_t .
\]
A histogram of category indices (0--9) is accumulated in parallel for UX badges.

\subsection{Monte Carlo error budget (HUD analogue to RTP)}

The HUD does \textbf{not} implement a house-banked game: there is no monetary \textbf{RTP} in the casino sense. The quantity $\hat{e}$ is an \textbf{equity} estimate (expected share of the pot at showdown under uniform completion of unknown cards). If $e$ denotes the true value of that expectation under the model, then $\mathrm{E}[\hat{e}]=e$ (each draw is independent and fair with respect to the remaining deck). Because $0\le S_t\le 1$,
\[
\mathrm{Var}(S_t)\le \frac{1}{4},
\qquad
\mathrm{Var}(\hat{e})=\frac{\mathrm{Var}(S_t)}{N},
\qquad
\mathrm{SE}(\hat{e})\le \frac{1}{2\sqrt{N}}.
\]
With the shipped default $N=2000$, $\mathrm{SE}(\hat{e})\le 1/(2\sqrt{2000})\approx 0.01118$ (about $1.1$ equity points at most in the worst-case variance bound).

\subsection{Quantum Combi---exact enumeration formula}

The promotional ``Quantum Combi'' category (documented for players in \path{Docs/final_report/QUANTUM_COMBI.adoc}) requires ranks $\{3,5,6,7,10\}$ each to appear \textbf{at least once} among the seven cards (two private + five community). All $\binom{52}{7}$ seven-card subsets are equally likely:
\[
\binom{52}{7} = 133784560 .
\]
For each rank $r$ in that set, let $A_r$ be the event ``no card of rank $r$ among the seven''; then $|A_r|=\binom{48}{7}$. By the principle of inclusion--exclusion over five ranks,
\[
\Bigl|\bigcup_{r} A_r\Bigr|
  = \sum_{k=1}^{5} (-1)^{k+1}\binom{5}{k}\binom{52-4k}{7}
  = 133002736 .
\]
Hence the favourable count is $133784560-133002736 = 781824$ and
\[
P(\text{Quantum Combi}) = \frac{781824}{133784560} \approx 0.00584 \approx 0.584\%.
\]

\subsection{Quantum Combi in the hand-ranking ladder (server and HUD)}

Both \path{server/src/logic/Evaluator.ts} and \path{client/src/utils/pokerHandCategory.ts} use the same \textbf{best-of-seven} cascade. Categories are integers $0$ (high card) through $9$ (straight flush); a larger packed score beats a smaller one. After ruling out straight flush ($9$), four-of-a-kind ($8$), and full house ($7$), the code tests \textbf{Quantum Combi before flush or straight}. Quantum applies iff every rank in $\{3,5,6,7,10\}$ appears at least once in the seven rank values (Ace is coded as $14$). Let $V$ be the multiset of those seven values; subtract one occurrence of each mandatory rank; sort the remaining values descending and take the top two as kickers $(\kappa_1,\kappa_2)$. The score is
\[
\texttt{packScore}(6,\kappa_1,\kappa_2) = 6\cdot 15^{5} + \kappa_1\cdot 15^{4} + \kappa_2\cdot 15^{3},
\]
padding unused kicker slots with zeros in the implementation. Only if Quantum fails does the evaluator continue to flush ($5$), straight ($4$), three-of-a-kind, two pair, one pair, high card. Thus Quantum is positioned \textbf{strictly between full house and flush}, as a design choice documented in \path{Docs/final_report/QUANTUM_COMBI.adoc}.

\section{Blackjack solo and multiplayer}
\label{app:bj}

\subsection{Solo blackjack engine}

Authoritative rules are implemented in \path{server/src/logic/blackjack.ts}. The server uses a six-deck shoe (\texttt{DECKS = 6}), shuffled in-place with Fisher--Yates (\texttt{shuffleShoe}). Card values follow standard rules: faces and tens count as $10$, aces count as $11$ when possible without exceeding $21$, otherwise as $1$. The dealer draws until the hard/soft total is at least $17$; because aces are valued optimistically, the dealer \textbf{stands on soft 17} (e.g.\ A+6). Natural blackjack pays a $3{:}2$ bonus on the stake (implemented as integer chip rounding per \path{intChips}); other wins pay $1{:}1$; pushes return the stake. Double down is permitted only with exactly two player cards and issues one extra card.

Solo routes: \path{server/src/routes/blackjack.routes.ts}. Multiplayer rooms and seats: \path{server/src/routes/blackjackMulti.routes.ts}, controllers under \path{server/src/logic/BlackjackTableController.ts}, in-memory runtime maps with recovery under \path{server/src/blackjack/}. UI: \path{client/src/pages/Blackjack.tsx}, lobby/table flows, components in \path{client/src/components/blackjack/}.

\section{Slot machine, roulette, and casino wallet}
\label{app:casino}

\subsection{Three-reel slot model}

The server module \path{server/src/logic/slotMachine.ts} draws three independent reels. Symbol weights are
\[
w_{\mathrm{cherry}}=32,\;
w_{\mathrm{lemon}}=24,\;
w_{\mathrm{bell}}=18,\;
w_{\mathrm{seven}}=14,\;
w_{\mathrm{diamond}}=8,\qquad
W=\sum_i w_i = 96 .
\]
One reel satisfies $\operatorname{Pr}[R{=}i]=w_i/W$. Triples satisfy $\operatorname{Pr}(R_1{=}R_2{=}R_3{=}s)=(w_s/W)^3$. Triple $s$ pays total return multiplier $m_s\in\{5,8,10,15,20\}$ on the stake; an \textbf{exact pair} (two equal symbols, third different) pays multiplier $1$ (stake returned, zero net profit); otherwise the payout multiplier is $0$. RNG is injectable (\texttt{RandomIntFn}, default \texttt{crypto.randomInt} via \path{server/src/rng/rng.service.ts}).

\subsection{Complete slot RTP (closed form, current constants)}

Let $X=\texttt{winAmount}/\texttt{bet}$ be the \textbf{gross return multiplier} (total coins returned by the machine, including the stake on a push). Write $R_1,R_2,R_3$ for the three reel symbols.

\paragraph{Triple (three of a kind).}
\[
\operatorname{Pr}(\text{triple of }s)=\Bigl(\frac{w_s}{W}\Bigr)^3,
\qquad
\operatorname{Pr}(\text{any triple})=\sum_s \Bigl(\frac{w_s}{W}\Bigr)^3=\frac{\sum_s w_s^3}{W^3}.
\]
Numerically $\sum_s w_s^3 = 32768+13824+5832+2744+512 = 55680$ and $W^3=96^3=884736$, hence
\[
\operatorname{Pr}(\text{any triple})=\frac{55680}{884736}\approx 0.0629\;(6.29\%).
\]

\paragraph{Exact pair (not a triple).}
For a doubled symbol $A$,
\[
\operatorname{Pr}(\text{pair with }A\text{ doubled})=\frac{3\,w_A^2\,(W-w_A)}{W^3},
\qquad
\operatorname{Pr}(\text{any pair})=\sum_A \frac{3\,w_A^2\,(W-w_A)}{W^3}.
\]
Numerically $\sum_A 3w_A^2(W-w_A)=461952$, so $\operatorname{Pr}(\text{pair})=461952/884736\approx 0.5221\;(52.21\%)$.

\paragraph{Lose.}
\[
\operatorname{Pr}(\text{lose})=1-\operatorname{Pr}(\text{triple})-\operatorname{Pr}(\text{pair})\approx 0.4149\;(41.49\%).
\]

\paragraph{Expected multiplier and RTP.}
Because outcomes partition $\{\text{lose},\text{pair},\text{triples}\}$,
\[
\mathrm{E}[X]
  =\sum_s \Bigl(\frac{w_s}{W}\Bigr)^3 m_s + \operatorname{Pr}(\text{pair})\cdot 1
  =\frac{\sum_s m_s w_s^3 + 461952}{884736}.
\]
Here $\sum_s m_s w_s^3 = 5\cdot32768 + 8\cdot13824 + 10\cdot5832 + 15\cdot2744 + 20\cdot512 = 384152$, so
\[
\mathrm{E}[X]=\frac{384152+461952}{884736}=\frac{846104}{884736}\approx 0.9563.
\]
The \textbf{return-to-player (RTP)} expressed as a percentage of the stake is $100\,\mathrm{E}[X]\approx 95.63\%$. The \textbf{house edge} on the stake is $1-\mathrm{E}[X]\approx 4.37\%$. The expected \textbf{net} gain per spin is $\mathrm{E}[G]=\mathrm{E}[\texttt{winAmount}-\texttt{bet}]=\texttt{bet}\,(\mathrm{E}[X]-1)\approx -0.0437\times\texttt{bet}$.

\paragraph{Variance (optional diagnostic).}
With the same $X$, the AsciiDoc reference reports $\mathrm{Var}(X)\approx 3.12$ (standard deviation $\approx 1.77$); hence $\mathrm{Var}(G)=\texttt{bet}^2\,\mathrm{Var}(X)$ for a flat bet. See \path{Docs/SLOT_MACHINE.adoc} for the full derivation.

\subsection{European roulette model}

The server module \path{server/src/logic/roulette.ts} draws a single winning integer uniformly from $\{0,\ldots,36\}$ (\texttt{crypto.randomInt} through the same RNG service). Payouts follow the European \textbf{total-return} multipliers on the stake for winning pockets (straight $36$, split $18$, street $12$, corner $9$, six-line $6$, dozen/column $3$, even-money $2$). Zero causes outside bets to lose unless covered.

\subsection{Complete roulette RTP (all proportional inside bets)}

Consider any bet line that covers exactly $k$ distinct winning pockets ($1\le k\le 18$ on the proportional ladder used in code) with European gross multiplier $m=36/k$ applied to the stake when one of those pockets hits. Because each pocket has probability $1/37$,
\[
\mathrm{E}\Bigl[\frac{\texttt{payout}}{\texttt{bet}}\Bigr]=\frac{k}{37}\cdot m=\frac{k}{37}\cdot\frac{36}{k}=\frac{36}{37}\approx 0.97297.
\]
Hence every such line has the same \textbf{RTP}${}=36/37\approx 97.297\%$ of the stake returned as gross payout in expectation, and the same \textbf{house edge}${}=1/37\approx 2.703\%$ on the stake. The expected \textbf{net} gain per unit staked on a single line is
\[
\frac{k}{37}\cdot m - 1 = -\frac{1}{37}.
\]
When several independent bet lines are placed on one spin, expectation adds across lines; the server enforces caps (\texttt{ROULETTE\_MAX\_BET\_CAP}, \texttt{ROULETTE\_MAX\_TOTAL\_STAKE}, \texttt{ROULETTE\_MAX\_BETS\_PER\_SPIN}) before settlement. Wheel animation order is \texttt{EUROPEAN\_WHEEL\_ORDER}. Full payout tables: \path{Docs/final_report/ROULETTE.adoc}.
